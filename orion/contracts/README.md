# ORION run-event contract (v1.2, reviewed 2026-11-04)

One contract joins the browser, the BFF routes and the agent: AG-UI events over server-sent
events, ORION's run view in `STATE_SNAPSHOT`, one action per turn, and the run record the BFF
serves. Design source: ORION RFA rev 25, mainly F1 (surfaces), F2 (states, answer anatomy,
interaction rules), F3 (choices), A2 (tools, APIs and events, data model), A3 (lifecycles) and
A4 (timeouts, modes). This file is meant to be implemented from without the design open.

Types live in two places that must match: `orion/agent/orion_agent/models.py` (Pydantic, the
source of the fixtures) and `.sources/frontend/src/features/orion/agui/types.ts`. Internal
Python interfaces for the builders are in `orion_agent/interfaces.py` and `orion_agent/tools/base.py`.

**v1.2 adds** (all additive to v1; schema ids stay `orion.run-view/v1` and `orion.run-record/v1`):
every resume action fully specified, `cancel` per status, `vizReports` riding on any turn,
`pending` pauses, run `cohorts`, follow-ups and open links, superseded plan versions, viz titles,
captions, frozen tables and the request-side parity hash, `defSha256`, the `save_cohorts` tool
call, the three BFF routes with the client's handling of their errors, the run record schema,
eleven codes, the finish status `Recorded`, fact chips for every on-screen number, one fact
format, the view's `environment` (mode H fingerprint), callIds, the 32 KB budget and fault
injection.

## Wire format

- One POST per turn. The response is `text/event-stream`.
- Each event is one frame, `data: <compact JSON>\n\n`, camelCase keys (ag-ui-protocol 1.0.0).
  **Every frame is at most 32 KB**, including the `data: ` prefix and the blank line.
  `TOOL_CALL_ARGS` and `TEXT_MESSAGE_CONTENT` deltas are at most 8,192 characters each.
- Readers ignore `event:`, `id:` and `retry:` fields and `:` comment lines, and accept `\r\n`.
- A response that is not `text/event-stream` (a BFF JSON error, a 307 redirect) is a transport
  error, not a run event (see "Client handling of BFF errors").
- Exactly one `RUN_FINISHED` or `RUN_ERROR` ends every invocation.

## Request: `RunAgentInput`

The browser sends it to the BFF, which forwards the bytes unchanged. All seven fields are always present.

```json
{"threadId": "<32 hex>", "runId": "<32 hex>", "state": {}, "messages": [{"id": "<id>", "role": "user", "content": "<question>"}],
 "tools": [], "context": [], "forwardedProps": {"orion": {"action": "ask", "...": "..."}}}
```

- Thread and run ids are 32 lowercase hex characters (128 random bits); anything else is rejected.
- `runId` names the run the action applies to: a new id for `ask`, the paused or target run for
  every other action, a fresh id for `warmup`.
- `messages` carries the question for `ask` and is empty otherwise.
- **`vizReports`** (optional on every action, at most 8): viz reports queued since the last turn,
  each `{"runId", "vizId", "mounted", "error", "pinnedHashVerified"}` for a run **of this
  thread**. `pinnedHashVerified` is true when the browser's recomputed `pinnedHash` equals both
  `pinnedHash` and `requestPinnedHash`, false when not, null when not checked. The agent records
  each report on its run before handling the action, following "Who writes a record": a report
  for a run whose task lives in another process is logged, not written. A report naming an
  unknown run, a run of another thread or an unknown viz is dropped and logged; it never rejects
  the turn. Reports that rode on a rejected turn are not recorded: the browser keeps them queued
  and sends them with its next turn.
- **When the browser sends a report.** A viz card queues its report when the viewer mounts or
  fails. If no invocation is open for the thread 2 s after the last queued report, the browser
  sends a standalone `viz_report` (one per report); otherwise reports ride on the next turn.

`cohortContext` (on `ask` and scope edits) is the browser's cohort snapshot, validated like planner output:

```json
{"active": {"id": "<cohort id or null>", "name": "All cases", "filters": {"mode": "and", "root": {}}, "caseCount": 1000},
 "saved": [{"id": "<cohort id>", "name": "<name>", "filters": {"mode": "and", "root": {}}, "caseCount": 334}]}
```

**The composer's scope chip** (before any run) is the client write `set_active_cohort`: picking
all cases or a saved cohort from the chip runs `setCurrentCohortId` in the click handler, after
an existence check, with an undo toast, and is logged with the thread id. The next `ask` carries
the result in `cohortContext`; `ask` has no scope field. The plan card's scope chip, once a run
exists, is a scope edit (below).

## Actions (`forwardedProps.orion.action`)

| Action | Payload | Run statuses that accept it |
| --- | --- | --- |
| `warmup` | none | no run (the turn creates none) |
| `ask` | `question` (1–4000), `cohortContext`, `cancelWaiting?` (a paused run's id) | new run |
| `cancel` | none | any (effect per status below) |
| `clarify_answer` | `optionId` | Clarifying |
| `consent` | `accept` (bool) | AwaitingConsent |
| `confirm` | `nonce`, `decision` (`create`/`dont_save`), `saved` (read-back), `makeActive` (ref or null) | AwaitingConfirmation |
| `edit_plan` | `field`, `value`, and `ref` or `cohortContext` per field (below) | Executing, AwaitingConfirmation, Answering, Complete, Partial, Limited, ObservedOnly |
| `retry_step` | `stepId` | Partial |
| `viz_report` | `vizId`, `mounted`, `error`, `pinnedHashVerified` | any |

`ACTION_STATUSES` in both type files holds the right-hand column.

### Checks, in order

Each check runs only if every earlier one passed, so no two overlap.

1. Malformed ids: a lone `RUN_ERROR INVALID_INPUT`, no `RUN_STARTED`.
2. Payload fails its schema: `INVALID_INPUT`.
3. The target run does not exist in this thread: `RUN_NOT_FOUND`.
4. The target run's lease expired (a leased status, Planning, Executing, Answering or Stopping,
   with a lapsed or missing lease, and no live task here): the run is recorded as of its lease's
   expiry, Cancelled if it was Stopping, Interrupted otherwise, and reported (see "Invocation
   outcomes"). The action is then checked against that status.
5. Busy: another run of the thread is unfinished, or the target run is leased by a controller in
   another process: `RUN_BUSY`. `viz_report` is exempt (its report is logged, not written, when
   the run is leased elsewhere).
6. The run cannot take the action now: its status does not accept it; `retry_step` or
   `edit_plan` on a run that is not the thread's latest; a `confirm` whose nonce is not the
   pending one and was never recorded (voided by an edit, or from another plan version):
   `STALE_ACTION`. A recorded nonce is not stale: it replays (below).
7. The action names something the run does not have: a `stepId` not in the current plan, a `ref`
   that is not a planned cohort, an `optionId` not offered, a `confirm` whose `saved` misses,
   repeats or adds a pending ref, a `vizId` the run never had, an edit field the plan cannot take
   (`method` or `thresholds` with no DE step, `topN` with no ranking or above the editable's
   `max`): `INVALID_INPUT`.
8. A known item in the wrong state: a step that is not Failed, or a Failed client step
   (`retry_step`); a `cohortName` edit for a cohort whose save is no longer `proposed`: `STALE_ACTION`.

`NOT_IMPLEMENTED` rejects an action whose capability is still stubbed.

**A new question at a pause.** The browser asks "Cancel the waiting run and send this, or keep it
waiting?" first. On Cancel it sends `ask` with `cancelWaiting` set to the paused run's id: the agent
ends that run Cancelled (as `cancel` would), sends its snapshot right after `RUN_STARTED`, then
streams the new run in the same invocation. Without `cancelWaiting`, an `ask` on a thread with a
paused run is `RUN_BUSY`; a `cancelWaiting` that names a run that is not this thread's paused run
is `STALE_ACTION`.

### Who writes a record

A run record has one writer at a time, its owner:

- the `RunWriter` of the task running the run, in the process that holds its lease; or
- for a run at rest (paused or ended, no lease), the invocation that accepted an action on it,
  under the thread lock, for that turn only.

Any other invocation routes what it records through the owner: when the run's task lives in this
process, ride-along reports and action-log entries go through that task's writer (staged, saved
with its next transition); when the run is leased by another process, they are logged (thread,
run, action, code), never written. A rejected invocation never writes a record: its rejection
appears in the log, and in the record's `actions` only when the run's task is in this process.
Writes that change no view field (reports, action-log entries, lease renewals) keep `revision`.

### What the agent emits on a resume

Every accepted resume (`clarify_answer`, `consent`, `confirm`, `edit_plan`, `retry_step`, and a
`cancel` that changes the run) streams `RUN_STARTED`, then **the run's snapshot with the action
applied** (revision + 1, `pending` null), then the run's usual events to its next pause or end,
then exactly one terminal event. The one exception is an edit that must wait for a running step
(below): heartbeats may come before its snapshot.

| Action | Effect |
| --- | --- |
| `cancel`, Planning or Executing or Answering | **Stopping at once** (a snapshot), then the in-flight call is aborted: the planner call (Planning; no plan is shown), the running step's tool request (Executing) or the composer call (Answering). Planner, composer and `ToolClient.call` honour asyncio cancellation; an aborted model call is a `modelCalls` entry with outcome `cancelled`, an aborted tool attempt a `calls` entry with status `error` and an `error` starting `CANCELLED`. The running step and every Queued step become Skipped "Not run: stopped"; finished steps keep their facts. Then Cancelled (`code` null), with Observed for the finished steps and `withheldReason` "you stopped the run" when there is any. The executor must abort within `STOP_GRACE_S` (5 s); after that the controller cancels it. |
| `cancel`, a waiting status | Cancelled at once: AwaitingUser and Queued steps Skipped "Not run: stopped", `pending` null, a pending nonce `voided`. |
| `cancel`, Stopping | The invocation joins the run's stream (its current snapshot first) and ends with the run. |
| `cancel`, an end status | The run's current snapshot and its terminal event; nothing changes. |
| `clarify_answer` | Status Planning. The planner runs again with the answer as a fixed slot (`interfaces.Clarification`); the run then streams like an `ask` from Planning. A second Clarify from the planner ends the run Limited with `AMBIGUOUS_REQUEST`. Clarify does not bump `plan.version` (there was no plan). |
| `consent` | `accept: true`: status Executing, `code` null, steps run; the `NAMED_TOOL_MISMATCH` limitation stays so the answer says why the tool changed. `accept: false`: queued steps Skipped "Not run: you declined the substitution", run ends Cancelled (`RUN_FINISHED Cancelled`). |
| `confirm` `create` | The applied snapshot shows the write step **Running**. `saved` lists every pending ref exactly once (else `INVALID_INPUT`, check 7; the run stays paused). The agent checks each read-back: `cohortId` and `name` non-empty, `defSha256` equal to the pending cohort's. A mismatch fails the write step (`WRITE_VERIFY_FAILED`), records the nonce `verify_failed` and ends the run Failed with `RUN_ERROR WRITE_VERIFY_FAILED`. On a match the write step runs Done (output such as "2 cohorts saved" or "1 saved, 1 reused"), each cohort becomes `save: saved` or `reused` with `cohortId` and `savedName`, the nonce is `accepted`, and later steps use the read-back names (DE's cache key includes them). `makeActive` is recorded only: the browser already switched the active cohort inside the click. |
| `confirm` `dont_save` | The applied snapshot shows the write step **Skipped** with `WRITE_SKIPPED` and the cohorts `save: skipped`; `saved` is empty and `makeActive` null. A `WRITE_SKIPPED` limitation is added, later steps use the proposed names, and hand-off is disabled for cards pinned to skipped cohorts. |
| `edit_plan` | See "The edit sequence". |
| `retry_step` | The failed read and every step Skipped because of it return to Queued; status Executing; `withheldReason` null; the step reruns as new calls (attempt numbers start again at 1, callIds continue); the `TOOL_FAILED` limitation goes when the step succeeds. Client writes never retry. |

**Idempotent `confirm`.** A `confirm` whose nonce the record already holds (`accepted` or
`verify_failed`) replays the recorded outcome and changes nothing: if the run's task is live
here, the invocation joins its stream; otherwise it sends the run's current snapshot and its
terminal event. A confirm lost after the browser saved (E19) is simply sent again; the browser's
save ledger keeps it from creating anything twice, and the BFF lets it through (see "Stop, edit
and confirm").

**A joining invocation** (a `cancel` of a Stopping run, a repeated `confirm`, a no-op edit while
the run's task is live here) sends the run's current snapshot right after `RUN_STARTED`, then the
run's live events. It drops a `STEP_FINISHED` whose `STEP_STARTED` it did not see.

**Standalone `viz_report`.** `RUN_STARTED`, then `RUN_FINISHED {"status": "Recorded", "code":
null}`; no snapshot, no status or revision change. An unknown `vizId` is `INVALID_INPUT`. The
record keeps the latest report per `vizId`.

### The edit sequence

1. If a step is running, the edit invocation waits for it to end, sending only heartbeats; a
   running step whose input hash version n+1 changes is cancelled at once under the Stop rule
   instead. A composer call in flight is aborted (outcome `cancelled`). Version n's step events
   never appear on the edit stream.
2. Plan version n+1 is compiled without a model call. Then one snapshot: status **Executing** (an
   edit makes no model call, so there is no Planning snapshot, and an ended run reopens straight
   to Executing), `plan.version` n+1, revision + 1, `superseded` gains `{planVersion: n, at,
   status, hadAnswer}`, `pending` null. A pending nonce is voided (`confirmations[]` gains it
   with `decision` null and outcome `voided`).
3. Each step of version n+1 whose input hash equals a finished version-n step's is **Reused**:
   `reusedFrom` names the version and step whose calls produced it (a step finished during the
   wait counts), and its facts carry over, renamed to the new step id and row if they moved
   (values and record hashes unchanged). Every other step is Queued. A write step that never ran
   pauses again with a new nonce.
4. The run streams on to its next pause or end. Version n's steps, facts, cohorts and answer move
   to the record's `superseded`.

**What an edit changes.** Every editable value is an argument of the steps it affects, so every
real edit changes the plan signature: the scope changes every step's arguments; `method` and
`thresholds` are arguments of `de_run` (`thresholds` also of `rank_top_n`); `topN` is the `n` of
`rank_top_n` or `top_mutated_genes`; a proposed cohort name is an argument of the write step (the
cohort's name) and of `de_run` (the group's name). **An edit is a no-op when the edited value
equals the current editable value** (`plan.editable`), whatever the signature: it changes
nothing, is logged `repeat`, and is answered like a repeated confirm.

### `edit_plan` fields

| `field` | `value` | Also | Applies to |
| --- | --- | --- | --- |
| `scope` | `{"source", "cohortName"?, "ledgerRef"?}`; absent keys are omitted, never null | `cohortContext` (required: the scope resolves against it) | the run's scope; the plan card's switch chip sends `plan.altScopeChoice` |
| `method` | `wilcoxon`, `edgeR` or `limma` | | the plan's DE analysis |
| `topN` | integer from 1 to the editable's `max` (100 for DE, 50 for top mutated genes) | | DE `top_n`, or top mutated genes `n`; the first analysis that takes one |
| `thresholds` | `{"pValueCutoff": 0<x≤1, "pValueType": "adjusted" or "original", "foldChangeCutoff": ≥0}` | | the DE thresholds the answer reports |
| `cohortName` | 1–100 characters | `ref` (required) | a planned cohort whose save is `proposed` (Rename on the confirmation card) |

`plan.editable` lists what the plan card may offer, each entry with its current value (and
`max` for `topN`).

## Events

| Type | Fields | When |
| --- | --- | --- |
| `RUN_STARTED` | `threadId`, `runId` | First event of every invocation whose ids are valid |
| `STATE_SNAPSHOT` | `snapshot`: a RunView | After every transition |
| `STEP_STARTED`, `STEP_FINISHED` | `stepName`: the step id, such as `s2` | Around each step; never before a snapshot with the plan |
| `TOOL_CALL_START`, `_ARGS`, `_END` | `toolCallId` = the pending nonce, `toolCallName` = `save_cohorts`, `delta` | At the confirmation pause (below) |
| `TEXT_MESSAGE_START`, `_CONTENT`, `_END` | `messageId` = `<runId>.v<planVersion>`, `role` = `assistant`, `delta` (≤ 8,192 characters) | After the last snapshot of a run that ends Complete or ObservedOnly, before `RUN_FINISHED` |
| `CUSTOM` | `name` = `orion.heartbeat`, `value` = `{"ts": "<ISO 8601>"}` | Every 15 s while the invocation streams |
| `RUN_FINISHED` | `threadId`, `runId`, `result` = `{"status", "code"}` | A waiting or end status, `Warmed` or `Recorded` |
| `RUN_ERROR` | `message`, `code` | A rejection, or the run ended Failed. No ids: it belongs to the invocation's run |

The text message is the verified answer as markdown (Observed, Interpretation, Hypotheses and
next steps, the withheld line, Limitations, then the notice; numbers as plain text written by
`format_fact`, no chips) for AG-UI clients. The ORION UI renders from snapshots and may ignore it.

### `save_cohorts` tool call

Sent once, in the invocation that reaches AwaitingConfirmation: after the snapshot whose status
is AwaitingConfirmation (write step `AwaitingUser`, `pending.kind` `confirm`) and before
`RUN_FINISHED AwaitingConfirmation`. The deltas concatenate to the JSON of the pending payload
with every `definition` present (`SaveCohortsArgs`):

```json
{"kind": "confirm", "nonce": "<32 hex>", "planSignature": "<sha256>", "planVersion": 1, "stepId": "s8",
 "cohorts": [{"ref": "kras_wt", "name": "KRAS not detected (ORION)",
              "definitionText": "Mutation-tested cases without a KRAS mutation, as a case-ID list",
              "definition": {"kind": "case_ids", "caseIds": ["SYNTH-CASE-0002", "…"]},
              "defSha256": "<sha256>", "caseCount": 520, "eligibleCount": 520, "reuse": null,
              "caseCountFactId": "f.s5.count", "eligibleCountFactId": "f.s7.eligible.control"}]}
```

On Create the browser, inside the click handler:

1. Recomputes `defSha256` for every saved cohort and reuses one that matches a pending cohort
   (re-checking the agent's `reuse`, since the store may have changed).
2. Writes a save ledger to localStorage keyed by the nonce, then calls `createNewCohort` for each
   cohort still missing, with the FilterSet below and the proposed name (made unique the way the
   Save Cohort modal does), diffs ids, reads back id and name, and refreshes counts. A resumed
   Create creates only cohorts missing from the ledger.
3. Recomputes `defSha256` from each saved cohort's stored filters and sends `confirm` with
   `saved: [{ref, cohortId, name, defSha256, reused}]` for every pending cohort.

The FilterSet the browser writes for a definition: `case_ids` becomes
`{"mode": "and", "root": {"case_id": {"operator": "in", "field": "case_id", "operands": [<sorted ids>]}}}`
(the platform's own case-list form). A `filter` becomes one root entry per field: an `in` clause
is `{"operator": "includes", "field", "operands"}`, a comparison is `{"operator", "field", "operand"}`,
and several clauses on one field are `{"operator": "and", "operands": [...]}`.

## Invocation outcomes

**Rejections.** `RUN_ERROR` with `INVALID_INPUT`, `RUN_BUSY`, `RUN_NOT_FOUND`, `NOT_IMPLEMENTED` or
`STALE_ACTION` rejects the invocation. No run is created, no run's status changes and no record
is written.

- With invalid ids, the whole stream is that one frame, without `RUN_STARTED`.
- With valid ids, the rejection follows `RUN_STARTED` directly.
- The client never shows a rejection as a Failed run. A rejected `ask` removes the optimistic
  run, puts the question back in the composer and shows a notice. Any other rejected turn leaves
  the run as its last snapshot showed it and shows a notice. `RUN_NOT_FOUND` for a `cancel` of a
  run the browser never received a snapshot of is handled like a rejected `ask`.

**Failures.** Every other `RUN_ERROR` code (`INTERNAL_ERROR`, `PLANNER_DECLINED`,
`WRITE_VERIFY_FAILED`, …) ends the invocation's run Failed.

**Expired leases.** A run whose lease expired is reported by the next invocation that touches it,
right after `RUN_STARTED`, recorded as of the lease's expiry (`updatedAt` = `lease.expiresAt`, or
the record's `updatedAt` without a lease; revision + 1):

- a **Stopping** run ends **Cancelled** (`code` null): Running, Retrying, Queued and AwaitingUser
  steps Skipped "Not run: stopped", `withheldReason` "you stopped the run" when it has Observed;
- any other run ends **Interrupted** (`code` `RUN_INTERRUPTED`): Running and Retrying steps Failed
  with code `RUN_INTERRUPTED`, Queued steps Skipped "Not run: interrupted", the limitation
  `{"code": "RUN_INTERRUPTED", "text": "The run stopped responding before it finished; completed
  steps are shown as partial.", "unblock": "Ask again.", "nearestApps": []}` appended,
  `withheldReason` "the run was interrupted" when it has Observed.

`pending` becomes null either way. If the invocation targeted that run, it ends `RUN_FINISHED`
with that status (`Interrupted`/`RUN_INTERRUPTED`, or `Cancelled`); an `ask` on the same thread
continues with its new run in the same stream. The BFF view route applies the same rewrite.

**Several runs in one stream.** A stream may carry snapshots of more than one run of the thread
(an expired-lease or `cancelWaiting` report first, status Interrupted or Cancelled). Readers apply
each snapshot to `snapshot.runId`; step, tool-call and text events belong to the invocation's run.

## RunView (the snapshot)


null: a segment's `factId`; a sentence's `dropped` and `cites`; a scope choice's `cohortName`
and `ledgerRef`; a volcano pin; and a limitation's `segments`.

- **`revision`** rises with every snapshot of a run; a reader keeps the highest one.
- **`plan`** is null while Planning. `plan.version` starts at 1 and rises only with an accepted
  `edit_plan`; the signature covers the compiled plan (every step's arguments) and its resolved
  scope, never named tools. `altScope` is the second scope a follow-up names after a cohort
  switch (E15) and `altScopeChoice` the scope edit value that switches to it (both or neither):
  the plan card shows both scopes and the chip sends `{"field": "scope", "value": altScopeChoice}`;
  the new version's `altScope` and `altScopeChoice` name the scope it left, so the chip can
  switch back. `steps` lists every step of the current version; a step carried over unchanged
  is `Reused`, with `reusedFrom: {planVersion, stepId}` (null for every other status).
- **`facts`** are the current version's facts so far. A step's facts appear in the first snapshot
  after it finishes (the Day 1 stub fixture shows them only at Answering, which is also valid).
  `value` is a number, or a string for a gene symbol or other name model text cites by placeholder.
  A fact id is also its placeholder, `{{f.s10.top.1.gene}}`.

  Limitations and the viz specs, with `interpretation` and `hypotheses` null and `followUps` and
  `openLinks` empty: the card shows "Writing interpretation". They fill only after the verifier

  model text carries no digit, no number word ("two groups" fails V-NUM) and no gene symbol; the
  V-NUM allow-list is the vocabulary's terms with digits (log2FC), app names (Gen3 Analysis) and

  verifier dropped stays as `{"segments": [], "dropped": "<rule>"}` and renders a marker.

  four analysis kinds, and a click asks `question` as a new turn) plus `openLinks` (Open `<app>`,
  click-only).

### Numbers on screen (FR-16, NFR-03)

Every tool-returned number the browser shows is a fact chip: a segment with a `factId`, or a
`…FactId` field beside the number. That covers Observed, model text, limitation lines (a
limitation that names one, such as an `INELIGIBLE_GROUP`'s eligible counts or a
`TIES_AT_CUTOFF`'s tied genes, carries `segments`, the same line with chips, which the card
renders instead of `text`), frozen table cells and notes, the scope line (it cites the `base`

(`caseCountFactId`, `eligibleCountFactId`). Titles, captions, `definitionText`, cohort names and

a step row is itself the source its numbers cite. Plan texts carry only the question's and the
plan's own settings ("Top 10", "adjusted p < 0.05"). The contract test scans every fixture for a
digit outside a fact segment, allowing only `Gen3`, `log2FC`/`log2`, `six-gene`, the panel genes
`TP53` and `DIS3`, the viewer's footnote `p = 0` and the Day 1 stub's withheld reason.

### Fact values on screen

`models.format_fact(value, unit)` is the one way a fact value is written, by the Observed
renderer, the verifier (when it resolves a placeholder into segment text) and TEXT_MESSAGE:

| Value | Text |
| --- | --- |
| A string (gene symbol, name) | Unchanged |
| Unit `p` | `0` for zero; below 0.001, one decimal of e-notation (`7.1e-60`, `2.1e-9`); otherwise three significant digits (`0.0342`, `0.05`) |
| Unit `log2FC` | Two decimals (`1.12`, `-0.87`, `0.00`) |

### Limitations and the nearest app

Every limitation carries `nearestApps` (`[{"appId", "title"}]`, catalog ids, possibly empty). The

### Size: 32 KB

A snapshot frame stays within 32 KB. Three caps keep the largest J3-shaped view inside it:

- **Ranked rows:** a view shows at most `VIEW_RANK_CAP` = **20** ranked rows in all (Observed's
  ranked lists and their facts, in plan order). A ranking with more rows adds one Observed
  sentence whose count is a fact ("Only the first part of the ranking is shown; all
  {{f.s10.count}} ranked genes are in the run record.", the `count` of `rank_top_n`'s output);
  the full ranking stays in the record's `calls` (Evidence Inspector).
- **Frozen tables:** at most `FROZEN_ROWS_CAP` = **10** rows (a DE card freezes to its top 10).
- **Model text:** at most 4 interpretation and 3 hypothesis statements of up to 300 characters
  each; follow-up labels up to 60 and questions up to 200 characters.

When a view is still larger, the agent (`events.fit_view`) trims, in this order and only as far
as needed: step `inputSummary` and `outputSummary` (clipped with "…" to 240, 80, 24, then 0
characters); then a pending confirm cohort's `definition`, set to null, largest first; then a
viz spec's `pinned`, set to null, largest first; then the question, plan paraphrase, row labels
and reasons, assumption and limitation texts (200, then 60 characters); last, fact labels, set to
"". Nothing else is ever trimmed: ids, revision, statuses, codes, the plan's rows, steps and
signature, facts (ids, values, units, pointers), every segment, sentence and `cites`, follow-ups,
open links, viz titles, captions, frozen tables and hashes, the pending nonce, signature, hashes
and counts, cohorts, the environment and the notice. A reader that finds a null pending
definition takes it from the `save_cohorts` args or the view route; a card that finds a null
`pinned` reads its spec from the view route before it mounts (its title, caption and frozen
table show at once). The view route and the record never trim. `tests/test_contract.py` builds
the largest allowed views (top N at 100 with 20 shown, 4,000 DE samples, the composer's maximum
text; and six pending cohorts of 10,000 ids) and asserts they fit. A view that still does not
fit ends the run Failed (`INTERNAL_ERROR`); a plan near the 20-call budget with several ranked
analyses can reach that, and the compiler should keep such plans inside the budget.

### Mode H fingerprint

In mode H the viewers read the local stack while the tools read AWS. The card computes the local
fixture fingerprint and freezes, saying why, when it differs from `environment.fingerprintSha256`.
The fingerprint is the sha256 of the canonical JSON (portable numbers) of this document, built
from the four sources `fixture_fingerprint` reads (`models.fingerprint_document`):

```text
{"schema": "orion.fixture-fingerprint/v1",
 "sandbox": {"status", "synthetic", "cases"},           // GET /sandbox/status (csrf left out)
 "analysis": {"version"},                               // GET /analysis/v0/_version
 "proteinpaint": {"pkgver", "codedate"},                // GET /protein-paint/healthcheck .versionInfo
 "ranking": [{"gene", "cases"}]}                        // the all-case topMutatedGenes ranking, in order
```

Launch dates and init status are left out, so a restart keeps the fingerprint.
`fixtures/fingerprint-vectors.json` holds the sources, documents, canonical strings and hashes.

### Canonical JSON (every hash)

Object keys sorted at every level (by code point), arrays in order, no whitespace, non-ASCII left
unescaped, `null` kept, an absent optional field omitted. Numbers are integers with |n| ≤ 2^53 − 1
or decimals with 1e-4 ≤ |x| < 1e15, which JavaScript and Python print identically; a number with
no fractional part prints as an integer (`2.0` as `2`). The fork's `viz/ppPinnedArgs.ts`
`canonicalJson` implements it. Record hashes (`requestSha256`, `responseSha256`) are the agent's
alone and allow any finite number.

## Cohort definitions and `defSha256`

A canonical cohort definition is one of:

```json
{"kind": "case_ids", "caseIds": ["SYNTH-CASE-0001", "…"]}
{"kind": "filter", "clauses": [{"field": "demographic.race", "op": "in", "values": ["black or african american"]}]}
```

`op` is `in`, `!=`, `>`, `>=`, `<` or `<=`; a clause's values are all strings or all numbers, and
exactly one unless `op` is `in`. Values are in the vocabulary's stored spelling. All cases is
`{"kind": "filter", "clauses": []}`. At most 10,000 case ids and 20 clauses.

`defSha256` = sha256 (lowercase hex) of the UTF-8 canonical JSON of
`{"schema": "orion.cohort-def/v1", ...normalized definition}`. Normalization:

1. `case_ids`: deduplicate, sort by code point.
2. `filter`: in each clause deduplicate and sort the values (numbers numerically, strings by code
   point); deduplicate clauses; sort clauses by field, then op, then the canonical JSON of values.
3. A filter that is exactly one `in` clause on `case_id` or `cases.case_id` becomes `case_ids`.

**Reading a saved cohort's FilterSet** (the browser, to find reuse matches; the agent, from
`cohortContext`): each root entry `key → operation` yields clauses for `operation.field` (or the
key). Operator `in` or `includes` with `operands` gives an `in` clause; `=` with `operand` gives an
`in` clause of one value; `!=`, `>`, `>=`, `<`, `<=` with `operand` give that clause; `and` with
`operands` reads each operand the same way. An operand `{"cases.case_id": "<id>"}` (ProteinPaint's
legacy form) is read as the id. A FilterSet cannot be read when it has `mode` `or` over more than
one key, any other operator (such as `excludes`), a non-scalar operand, more than 20 clauses, or
a number outside the canonical range (such as 0.00005): it has no `defSha256` and never matches,
and reading it never raises. `fixtures/cohort-def-vectors.json` holds both kinds of input
(`definition` and `filterSet`) with their expected `canonical` and `sha256` (null when unreadable).

## Statuses and codes

### RunStatus (15)

`Planning`, `Clarifying`, `AwaitingConsent`, `Executing`, `AwaitingConfirmation`, `Stopping`,
`Answering`, `Complete`, `Partial`, `Limited`, `Unsupported`, `ObservedOnly`, `Cancelled`,
`Failed`, `Interrupted`. Snapshots carry all fifteen. `RUN_FINISHED` carries the three waiting
statuses and every end status except `Failed` (which ends with `RUN_ERROR`), plus `Warmed` and
`Recorded` for turns that touch no run status. It carries `Interrupted` only when the invocation
targeted a run whose lease expired.

**Leases.** `LEASED_STATUSES` (both type files) are Planning, Executing, Answering and Stopping:
a record in one of them holds `lease {owner, renewedAt, expiresAt}`. While Planning, Executing or
Answering (`RENEWED_STATUSES`) the controller renews it every 30 s, expiring 180 s after the last
renewal. Entering Stopping sets a lease that lapses `STOP_LEASE_S` (30 s) later and is never
renewed: Stop aborts the in-flight call at once, so a live controller ends the run well before.
Every other status clears the lease.

## BFF routes

Three same-origin Next.js API routes in the fork, `src/pages/api/orion/`. The BFF holds no run
state: it tracks only each thread's open upstream call. It never writes a run record.

**Ids.** Every route checks `threadId` and `runId` against `^[0-9a-f]{32}$` before anything else.

**Errors.** Every route answers an error with JSON, never an event stream:
`{"error": {"code": "<BffErrorCode>", "message": "<text>"}}`.

| Condition | HTTP | `code` |
| --- | --- | --- |
| Body not JSON, a field missing, an id malformed | 400 | `INVALID_INPUT` |
| A view or record that does not exist (or whose `threadId` differs) | 404 | `RUN_NOT_FOUND` |
| A second turn for a thread whose upstream call is still open (not `cancel`, `edit_plan` or `confirm`), or AgentCore 409 | 409 | `SESSION_BUSY` |
| Upstream non-2xx before the stream starts (other than 409, 429, 503) | 502 | `UPSTREAM_ERROR` |
| Upstream unreachable, 429 or 503 | 503 | `UPSTREAM_UNAVAILABLE` |
| No first byte within 30 s | 504 | `UPSTREAM_TIMEOUT` |

### Client handling of BFF errors

The transport (`agui/transport.ts`) parses the `BffError` body of any non-SSE response and hands
its `code` to the controller, which acts by code:

| `code` | The browser |
| --- | --- |
| `INVALID_INPUT` (400) | Treats the turn as rejected (as a rejected `RUN_ERROR` turn: an `ask`'s question goes back to the composer). |
| `SESSION_BUSY` (409) | Polls the target run's view route every 2 s for up to 30 s until the run is not in a leased status. It resends the turn, unchanged, only if the action still applies (the run still waits for it: same status, same pending nonce); otherwise it shows the run as the view route has it. For an `ask` (no run yet): a view 404 means the ask never started, so it resends with the same `runId`; a 200 means it started, so it follows the view route. |
| `UPSTREAM_TIMEOUT` (504), `UPSTREAM_ERROR` (502) | GETs the view for the turn's `runId` before deciding: a 200 shows that run (an `ask` may have started its run), and the run is then followed by polling; a 404 treats the turn as rejected. Never resends an `ask` under a new `runId`. |
| `UPSTREAM_UNAVAILABLE` (503) | Treats the turn as rejected with a notice that ORION is unavailable; an `ask`'s question goes back to the composer. |
| `RUN_NOT_FOUND` (404, view or record) | The run is not stored (yet): on restore, drops it from the thread; in the Evidence Inspector, says the record is not available. |

A stream that ends with no terminal event (the BFF never invents a frame) is restored from the
view route, as above.

### `POST /api/orion/agui`

- Body: `RunAgentInput`. Response: `200`, headers `Content-Type: text/event-stream; charset=utf-8`,
  `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`; the upstream's bytes relayed
  unchanged and flushed per chunk (heartbeats included), no compression.
- Session id: `orion-<threadId>` (38 characters). AgentCore's `runtimeSessionId` must be at least
  33 characters, so the bare 32-character thread id cannot be used; mode L uses the same value.
- **Mode L:** `POST ${ORION_AGENT_URL:-http://orion-agent:8080}/invocations` with
  `Content-Type: application/json`, `Accept: text/event-stream`,
  `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id: orion-<threadId>` and the browser's `traceparent`.
- **Modes A and H:** `InvokeAgentRuntime` on `ORION_RUNTIME_ARN` (qualifier
  `ORION_RUNTIME_QUALIFIER`, default `DEFAULT`, region `AWS_REGION`, us-east-1) with
  `runtimeSessionId` `orion-<threadId>`, `contentType` `application/json`, `accept`
  `text/event-stream`, `traceParent`, and the body bytes as `payload`; the response stream is
  relayed unchanged. Credentials: the developer profile (H) or the `orion-bff` Pod Identity role (A).
- **No disconnect forwarding.** A browser disconnect never aborts the upstream call; the BFF keeps
  reading it to its terminal event and discards the rest, so the run finishes in its record.
- **Stop, edit and confirm.** A turn whose action is `cancel`, `edit_plan` or `confirm` for a
  thread with an open upstream call first aborts that call (the agent's run continues detached;
  the abort frees the session), then sends the new turn. A resent `confirm` (E19) therefore
  reaches the idempotent path instead of `SESSION_BUSY`. For `cancel` in modes A and H, if no
  snapshot of the run with status `Cancelled` arrives within 10 s, the BFF calls
  `StopRuntimeSession` for the session. The grace is short because the controller aborts the
  in-flight call at once; if `StopRuntimeSession` kills it mid-Stopping, the run's Stopping lease
  lapses within 30 s, the view route then shows it Cancelled, and the browser's resent `cancel`
  (with its next turn) records it Cancelled.
- After the stream started, an upstream failure just ends the response; the BFF never invents a
  frame. The browser sees a stream with no terminal event and restores from the view route.

### `GET /api/orion/runs/[runId]/view`

Optional query `threadId` (must match the record's). Returns `200 application/json`,
`Cache-Control: no-store`, body: the record's `runView` (the view as of the last transition,
untrimmed, so it may exceed 32 KB), with the **expired-lease rule** applied: when the record's
`status` is a leased status (Planning, Executing, Answering, Stopping) and its `lease` is null or
`lease.expiresAt` ≤ now, the route returns the view rewritten exactly as "Expired leases" above
describes (revision + 1, `updatedAt` = `lease.expiresAt` or the record's `updatedAt`, Cancelled for
Stopping, Interrupted otherwise), which is exactly what the controller records on the next turn.
A record with no `runView` answers 404. Used to reconnect after a dropped stream, to restore the
thread on return, and to read a snapshot's trimmed `pinned` inputs and pending definitions.

### `GET /api/orion/runs/[runId]/record`

Optional `threadId` as above. Returns the stored run record unchanged (`orion.run-record/v1`,
FR-20 export), `200 application/json`, `Cache-Control: no-store`; with `?download=1` also
`Content-Disposition: attachment; filename="orion-run-<runId>.json"`. No lease rewrite: the
record's own `lease` shows a lapse. The Evidence Inspector reads full step outputs here.

## Run record (`orion.run-record/v1`)

The record route's body; `fixtures/run-record.j1-complete.json` and `run-record.j1-retry.json`
are complete examples. One record per run, rewritten after every transition with a rising
`revision`; the Runtime is its only writer (see "Who writes a record").

**callIds.** A tool call attempt is `<runId>.v<planVersion>.<stepId>.c<n>`, n counting every
attempt of that step in that plan version (a retry takes the next n, and so does a `retry_step`
rerun; `attempt` keeps its own count, 1 or 2 within one call). A model call is
`<runId>.planner.c<n>` or `<runId>.v<planVersion>.composer.c<n>`. Every callId in a record is unique.

| Field | Type | Notes |
| --- | --- | --- |
| `schema`, `threadId`, `runId`, `revision`, `status`, `code`, `question`, `createdAt`, `updatedAt` | | As in the view |
| `environment` | `{mode, planner, executor, agentVersion, toolTransport, fingerprintSha256, faults}` | `toolTransport` `in_process` or `gateway`; the fingerprint of s1, null until it ran; `faults` the ORION_FAULTS in force (`<target>:<kind>`, sorted), empty in a real run |
| `lease` | `{owner, renewedAt, expiresAt}` or null | Set only in a leased status |
| `request` | the `ask` action | The question and cohort context as received |
| `plannerOutput` | IR (snake_case, `orion_agent/ir.py`) | The latest planner output: Plan, Clarify or Unsupported |
| `planVersions` | `[CompiledPlan]` | `{version, signature, scope{source, name, caseCount, clauses}, rows, steps[{id, row, tool, kind, folded, inputSummary, args, dependsOn}], assumptions, limitations, writes, paraphrase, altScope, altScopeChoice, editable}`; every editable value is in some step's `args` |
| `planHistory` | `[{version, cause, at, ir, edit}]` | Why each version exists: `ask`, `clarify_answer` or `edit_plan`, with the IR it compiled and the edit |
| `modelCalls` | `[{callId, role, model, fallback, effort, attempt, startedAt, elapsedMs, outcome, stopReason, inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens}]` | Every planner and composer call, refusal fallback and repair included; `model` names the model that served; `outcome` `ok`, `refused`, `invalid`, `error` or `cancelled` |
| `steps` | `[Step]` | The current version's steps. A step's calls are the `calls` with its `planVersion` and `stepId`, or, for a Reused step, its `reusedFrom`'s |
| `calls` | `[{callId, planVersion, stepId, tool, transport, attempt, startedAt, request, requestSha256, httpStatus, responseSha256, elapsedMs, status, observed, warnings, limitation, error, provenance}]` | One entry per attempt of every counted call (server tool, pure function, client write), aborted attempts included (status `error`, `error` starting `CANCELLED`). `observed` is the full output (null when the attempt returned nothing); `requestSha256` and `responseSha256` hash the canonical JSON of `request` and `observed`; `provenance` lists each HTTP request `{method, path, requestSha256, httpStatus, responseSha256, elapsedMs}` |
| `facts` | `[Fact & {planVersion, callId, requestSha256, responseSha256, engine}]` | The view's facts plus where each value came from: `callId` is the attempt whose result was used (for a Reused step, the original call); `jsonPointer` is into that call (`/observed/...`) |
| `cohorts` | `[CohortView & {definition}]` | The canonical definitions behind `defSha256` |
| `pending` | Pending or null | The open pause with every definition present |
| `confirmations` | `[{nonce, decision, saved, makeActive, at, outcome}]` | `accepted`, `verify_failed` or `voided` (`decision` null: an edit or a cancel replaced the pause); what makes `confirm` idempotent |
| `vizReports` | `[{vizId, mounted, error, pinnedHashVerified, at}]` | The latest per viz |
| `actions` | `[{at, action, outcome, code}]` | The turns that touched the run: `accepted`, `repeat` or `rejected` (see "Who writes a record") |
| `ledger` | `{follows, refs[{runId, ref, name}]}` | What the run took from the session ledger |
| `answer` | `{observed, limitations, interpretation, hypotheses, withheldReason, vizSpecs, followUps, openLinks, notice}` | The view's answer parts, untrimmed (every `pinned` present) |
| `superseded` | `[{planVersion, at, status, steps, facts, cohorts, answer}]` | What each edit replaced, in full |
| `runView` | RunView or null | The view as of the last transition, untrimmed: the view route serves it |

The view is a projection of the record: `plan` is the last `planVersions` entry without `steps`,
`limitations` and scope clauses; facts drop their provenance fields; cohorts drop `definition`;
`pending` shows only in a waiting status; `superseded` keeps its summary; `environment` keeps
`mode` and `fingerprintSha256`.

## Tool envelope (agent internal)

Server tools, pure functions and client actions share one result shape, `ToolResult`, also the
JSON the Gateway Lambda returns for `vlab___<tool>`:
`{"status": "ok"|"empty"|"error"|"unavailable", "observed", "warnings", "limitation", "provenance", "error"}`.
`empty` is a zero result, never success with no rows. Full outputs stay inline: each tool caps its
response below Lambda's 6 MB synchronous limit and the record keeps it in `calls[].observed` (the
design's `ArtifactRef` is not part of the MVP). The ToolClient (in-process or Gateway) returns a
`ToolCallOutcome` with every attempt, each with its own callId; each attempt becomes a `calls`
entry. It honours asyncio cancellation (an aborted attempt is a `CANCELLED` tool error, never
retried). Types, guards, the A4 timeout budget (55 s HTTP, 58 s Lambda, 60 s step, 130 s cap, one
retry on 429, 502, 503, 504 or a timeout with an identical body, 10–20 s backoff on 429) and the
pure-function signatures are in `orion_agent/tools/base.py`.

The run controller's collaborators are in `orion_agent/interfaces.py`: `Planner`, `Executor` with
its `StepSession` (`start_step`, `retrying`, `finish_step` with the step's facts, calls and
cohorts, `skip_step`, `reuse_step`, `wait_stop`, and `resume`, the `ResumeState` a confirm,
retry, consent or edit starts from), the extractor, the Observed renderer, `Composer.compose(question,
facts, plan, observed, allow_list=, ledger=, feedback=)` with the verifier's V-NUM allow-list,
the `Verifier`, and the ledger store.

### Fault injection (E11)

`ORION_FAULTS` holds comma-separated `<target>:<kind>` pairs, such as
`de_run:timeout,planner:refuse,composer:refuse,cohort_count:empty`. A target is a server tool
(`timeout`, `error`, `empty` or `cache_busy` replace its HTTP call; a `timeout` fails each
attempt as the 55 s HTTP timeout would, without waiting it out, so the step retries once and fails) or a model role, `planner` or `composer`
(`refuse`: both models refuse). The agent honours it only in mode L (`ORION_MODE=L`) or a test
Runtime (`ORION_TEST_RUNTIME=1`) and refuses to start otherwise; the record's
`environment.faults` lists the faults in force (`orion_agent/settings.py`).
