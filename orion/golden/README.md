# ORION golden request bodies

Request bodies captured once from the native Virtual Lab viewers, so ORION's server tools and
each card's parity badge can be contract-tested against what the viewers really send (RFA rev 25,
A2 "Tools": "Golden bodies are request bodies captured once from the native viewers and
contract-tested"; Risks: "Chart and answer drift apart").

Generated by `orion/scripts/golden-capture.mjs`. Do not edit the JSON by hand; rerun the script.

## Running

Needs the local stack (`mmrf-synthetic`) up and the gateway on `http://127.0.0.1:3080`.

```sh
npm ci                                       # root devDependency @playwright/test 1.58.2
npx playwright install chromium
node orion/scripts/golden-capture.mjs        # capture, write changed files, print a summary
node orion/scripts/golden-capture.mjs --check  # capture, write nothing, exit 1 on any drift
```

`SANDBOX_ORIGIN` overrides the origin; only `http://localhost` or `http://127.0.0.1` is accepted.
Each run uses a fresh headless Chromium profile (all cases, no saved cohorts) and takes about
25 seconds. The summary marks each file `new`, `unchanged` or `changed`, and lists the viewer
setup requests it saw but did not keep (genomes, termdb/config, termchildren, categories, cohorts).
On failure it writes a screenshot and every captured request to a fresh `orion-golden-capture-*`
directory under the OS temp directory and prints its path.

| File | Viewer and flow | Request(s) |
| --- | --- | --- |
| `proteinpaint/termdb-survival.json` | Correlation Plot, J1 by hand: primary variable "Synthetic overall survival", overlay "CGS risk category", Submit | `GET /protein-paint/termdb/survival` |
| `proteinpaint/termdb-topMutatedGenes.json` | OncoMatrix default view, all cases | `GET /protein-paint/termdb/topMutatedGenes` |
| `proteinpaint/termdb-matrix.json` | OncoMatrix default view, all cases | `POST /protein-paint/termdb/matrix` |
| `proteinpaint/termdb-getsamplecount.json` | DE: Add group "KRAS mutation status" is "No mutation", then a second group "Mutated" | 2 x `GET /protein-paint/termdb?getsamplecount=1` |
| `proteinpaint/termdb-getsamplelist.json` | DE: Submit (New group vs New group 1) | 2 x `GET /protein-paint/termdb?getsamplelist=1`, group order |
| `proteinpaint/termdb-DE-preAnalysis.json` | DE: Submit (New group vs New group 1) | `POST /protein-paint/termdb/DE` with `preAnalysis: true` |

DE groups follow `scripts/ui-scenarios.mjs` (Add group, pick a dictionary term, tick a value,
Apply). Group 1 ("New group", shown as CONTROL) is KRAS "No mutation", 520 samples; group 2
("New group 1", CASE) is "Mutated", 480 samples. The script asserts that edgeR is preselected
before it switches to Wilcoxon.

## Format (`orion.golden/v1`)

```json
{"schema": "orion.golden/v1", "kind": "proteinpaint/termdb-survival", "viewer": "...", "flow": "...",
 "stage": "pre-bridge", "proteinpaintServer": "2.216.0", "normalized": ["query.embedder", "..."],
 "requests": [{"step": "correlation-survival", "method": "GET", "path": "/protein-paint/termdb/survival",
               "query": {"genome": "hg38", "...": "..."}, "body": null, "payloadSha256": "<hex>",
               "response": {"status": 200, "bytes": 91229, "sha256": "<hex>"}}]}
```

- `requests` keeps the order the browser issued them. `step` is the capture step that issued it.
- `path` is the gateway path, prefix included.
- `query` is set for a GET: each query parameter value is JSON-parsed exactly as
  `identity/server.mjs` does before bridging (a value that is not JSON stays a string). The script
  checks that every parsed value re-encodes to the exact bytes sent, so nothing is lost.
- `body` is set for a POST: its JSON body. A request never has both.
- `payloadSha256` is the sha256 of the normalized payload (`body`, or `query` for a GET) as
  canonical JSON: object keys sorted at every level, array order kept, no whitespace. It is a
  drift check for this capture, not the parity badge's hash definition, which is still open.
- `response.bytes` and `response.sha256` describe the decoded response body (after HTTP
  compression) once the response normalizations below are applied; with none, they are the raw
  bytes. They tie each golden to this fixture (synthetic data, seed 42) and will change if the
  data, generator or ProteinPaint version changes.
- `proteinpaintServer` comes from `GET /protein-paint/healthcheck`. The client is
  `@sjcrh/proteinpaint-client` 2.216.0, per the fork's `package-lock.json` at 27cf09a.

### Pre-bridge, and GET versus POST

These are the requests the browser sends to the identity gateway, before it bridges them. For any
`/protein-paint/*` request carrying `filter0`, `filter` or `samplelst`, the gateway rewrites those
keys into native sample-list filters and drops `filter0` before ProteinPaint sees the request; it
also turns such a GET into a JSON POST of the same parsed parameters. A server tool that sends a
golden payload through the same gateway (as a JSON POST, as the RFA's tool table states) is bridged
the same way, so ProteinPaint receives the same request. ProteinPaint's `dofetch3` sends small
requests as GET with JSON-encoded query values and switches to POST only for long URLs, which is
why survival, topMutatedGenes, getsamplecount and getsamplelist are GETs here while matrix and both
DE calls are POSTs.

## Normalizations

Only fields that differed between two runs on the same stack, or that depend on the host the page
was loaded from, are normalized. Each file lists the ones applied to it under `normalized`.

| Field | Replaced with | Why |
| --- | --- | --- |
| `query.embedder`, `body.embedder` (survival, matrix) | `"<page hostname>"` | `dofetch3` sends `location.hostname`: `127.0.0.1` here, the CloudFront host in AWS. The synthetic dataset has no `dsAuth`, so ProteinPaint does not use it |
| `$id` of term wrappers matching `TwBase_<n>__<a>_<b>` (`query.term2.$id`, `body.terms[*].$id`) | `TwBase_<n>_<page load>` | The bundled client builds it as `` `TwBase_${counter}_${E}` `` with `` E = `_${Math.random()…}_${Date.now()…}` `` fixed per page load. The counter `n` is creation order and stable, so it is kept. The survival `term1.$id` (`+JMEWl6…`) is content-derived and stable, so it is kept |
| Matrix response: echoed `$id` values | the same `TwBase_<n>_<page load>` | ProteinPaint keys `refs.byTermId` by the request's `$id`s |
| Matrix response: term `shortId` | the term's 1-based position in `body.terms` | The response streams one `[path, value]` JSON line per sample, keyed by `shortId`. The server numbers terms in the order its parallel per-gene queries finish (KRAS and NRAS swapped between runs), so it is renumbered and each line re-serialized. The data is otherwise identical |
| `/analysis/v0/survival/` response: `results[*].meta.id` | `"<python object id>"` | Gen3 Analysis sets it to a Python `id()`, a memory address that changes on every call |

Not normalized, but worth knowing when building tool bodies or the parity hash:

- `termdb-DE-wilcoxon.json` `volcanoRender.devicePixelRatio` is `window.devicePixelRatio * 2`:
  2 here (headless Chromium at scale 1), 4 on a typical Retina display. It only affects the
  volcano PNG. `deKeyInputs` in the running 2.216.0 server, the DE cache key, leaves out
  `volcanoRender`; it keys on `genome`, `dslabel`, canonical `samplelst`, `min_count`,
  `min_total_count`, `cpm_cutoff`, `method`, `pseudobulk`, `tw`, `tw2`, `filter` and `filter0`.
- DE group names (`New group`, `New group 1`) are the UI defaults and are part of that cache key;
  ORION's `de_run` names groups with the saved cohort names instead.
- `samplelst` values are ProteinPaint integer `sampleId`s, ordered as `getsamplelist` returned them.
- The `filter` of getsamplecount and getsamplelist carries UI fields from the value picker
  (`samplecount`, `bar_width_frac`) inside each `tvs` value.
- All-cases `filter0` is `{"and": []}`, never null, in every ProteinPaint request captured here,
  including both DE calls (the groups came from dictionary terms, not saved cohorts).
- The ProteinPaint survival request sends `term1` and `term2` (not `term`) and no `filter`.

## `/analysis/v0/survival/`

The Correlation Plot's J1 flow calls only ProteinPaint (`termdb/survival`); no `/analysis/` call.
In the fork's source, `/analysis/v0/survival/` is called only by Clinical Data Analysis
(`src/features/cDave/Dashboard.tsx` for the Overall Survival card and
`CDaveCard/ClinicalSurvivalPlot.tsx` for a card's survival toggle). Both are captured. The sandbox's
Clinical Data Analysis has no CGS risk field, so the two-group body shape comes from the Sex card
(its top two values, female and male): `{"filters": [{"and": [{"=": {"demographic.gender":
"female"}}]}, {"and": [{"=": {"demographic.gender": "male"}}]}]}`. Two related endpoints are not
captured: `/analysis/v0/survival/compare` (Cohort Comparison) and
`/analysis/v0/survival/compare_genomic` (Mutation Frequency).

## Stability

After the normalizations above, consecutive runs against the same stack produce byte-identical
files; `--check` exits 0 when nothing drifted.
